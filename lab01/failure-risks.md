# Failure risks · ITC Club Hub (v0.1, 2026-10-21)

| # | How the project could fail | Chapter 01 topic | Early warning sign | First countermeasure | Owner |
|---|---|---|---|---|---|
| F1 | We overcomplicate the C++ backend for the booking logic and get stuck in a maze of buggy data structures. | Essential difficulties | Debugging takes up our whole week and we start drowning in confusing pointer errors or broken references. | Scrap the smart automated logic and switch to a simple, manually updated text log instead. | 
| F2 | Everyone works on their own features in isolation, making it impossible to merge our code together later. | Scale and communication | Git merge conflicts become an absolute nightmare and different parts of the code stop talking to each other. | Freeze new features for two days, jump on a group call, and fix the core data interfaces together. | 
| F3 | We listen to too many random feature requests from classmates and completely lose track of our actual assignment. | Changing requirements and cost of change | Our feature list keeps growing longer every week while our actual core assignment sits unfinished. | Put a hard lock on the feature list and push any new, flashy ideas to a "nice-to-have later" backlog file. | 
| F4 | The terminal app completely crashes or corrupts saved club files right before we are supposed to demo it. | Reliability, security and safety | The CLI app randomly throws segmentation faults whenever we test unexpected text inputs or empty fields. | Write quick test cases checking weird inputs (like empty spaces or massive strings) before writing heavy logic. | 
| F5 | We write messy, unreadable code early on, making it a nightmare to add simple features near the deadline. | Legacy, integration and technical debt | It takes an entire afternoon of rewriting code just to add one simple new data field to a club profile. | Schedule a dedicated cleanup session halfway through the project to untangle messy files and add clear comments. |
